# Baseline: 2026-10-21, 10k versions

## Setup

- **Commit:** the #103 harness on top of the facet and reference work. The reference chain was #138–#147 at the time, not yet merged.
  - The harness commit was `6a5fadf5`, a local commit later rebased away, so it is on no branch.
  - The run did not record its exact SHA, and the raw report was not kept.
  - The [post-#156 baseline](baseline-2026-10-21-post-156.md) records both, and supersedes this one for comparisons.
- **Command:** `ASTER_BENCH_VERSIONS=10000 dotnet run -c Release --project bench/Aster.Benchmarks -- --filter '*'`
- **Job:** `ShortRun` (3 warmups, 3 iterations, 1 launch). Treat differences under about 20% as noise.
- **Hardware:** cloud VM, Intel Xeon 2.80 GHz, 4 cores, Ubuntu 24.04.
- **Runtime:** .NET 10.0.13 (SDK 10.0.402).
- **Data:**
  - 10,000 resource versions in total: 2,475 articles × 4 versions, plus 100 authors.
  - About 3 KB of aspect payload per version.
  - Half the articles are active in `published`.
- **SQLite:** a temporary file database with default provider options.

Queries return at most one page of 50 latest versions.

## Findings

1. **Single-resource operations are O(tenant size).** This blocks scale. `DefaultResourceManager` reads every version in the tenant and then filters to one resource in memory. On SQLite, a get-latest therefore deserializes the whole store: 249 ms and 113 MB at 10k versions. The in-memory provider shows the same shape at smaller constants. Tracked in #154. Until it is fixed:
   - The 100k and 1M runs this harness was built for are not meaningful. At 1M, a single SQLite read would take tens of seconds.
   - The resource rows above measure the scan, not the operation.
2. **SQLite array queries and reverse lookups cost roughly 10× scalar facet queries,** at about 135 ms each. Both enumerate `json_each` over every latest version, with no index to narrow it. Index projections (#100) and the SQL Server design in ADR 0004 (materialized `projection_values`) are the intended remedies. Re-measure once SQLite gets projection-backed indexes.
3. **SQLite import preview (144 ms) costs 25× SQLite export (5.8 ms).** The preview reads the target state of every imported resource. It likely shares the unbounded read pattern from finding 1; #154 includes it in its audit.
4. **The in-memory provider is fast enough everywhere** for tests and development. Nothing here needs action beyond the shared fix in #154.
